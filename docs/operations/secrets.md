# إدارة الأسرار (H7.3)

**القرار المعتمد:** متغيرات بيئة المنصّة — **GitHub Secrets** للـCI/CD، ومتغيرات بيئة منصّة النشر للإنتاج.
**لا Vault ولا Doppler في هذه المرحلة.**

هذا المستند هو المصدر الوحيد لتعريف «من أين تأتي الأسرار» في كل بيئة.

---

## 1) المبدأ

- **لا سرّ في المستودع إطلاقًا.** لا في الكود، ولا في `.env` مُلتزَم، ولا في الصورة.
- `apps/api/.env.example` **قالب فقط** بقيم نائبة (`change-me-in-production`) — لا يحوي سرًّا حقيقيًا.
- `.env` مُستثنى في `.gitignore`، و`.dockerignore` يمنع تسربه إلى صورة Docker.
- الأسرار تُحقن **وقت التشغيل** كمتغيرات بيئة، فتُبدَّل بلا إعادة بناء.

### ما يتحقق من ذلك آليًا

- **H0.1** — `parseEnv()` يفشل الإقلاع فورًا إن غاب `JWT_SECRET`/`DATABASE_URL`،
  ويرفض في الإنتاج السرّ الافتراضي/الضعيف أو الأقصر من 16 حرفًا.
- **H3.1** — السجلات تحجب `authorization` و`cookie` وحقول `password`/`token`
  (`lib/logger.ts`)، فلا يتسرّب سرّ إلى مجمّع السجلات.

---

## 2) جرد الأسرار

| المتغير | حسّاس؟ | المصدر في الإنتاج | ملاحظات |
| --- | --- | --- | --- |
| `JWT_SECRET` | 🔴 نعم | متغير بيئة المنصّة | عشوائي ≥32 حرفًا. تدويره يُبطل كل الجلسات. |
| `DATABASE_URL` | 🔴 نعم | متغير بيئة المنصّة | يحوي كلمة مرور القاعدة. |
| `REDIS_URL` | 🟠 غالبًا | متغير بيئة المنصّة | قد يحوي كلمة مرور. |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | 🔴 نعم | **يُفضَّل عدم استخدامهما** | استخدم **دور IAM** للمهمة/الخادم بدلًا منهما. |
| `S3_BUCKET` / `S3_PREFIX` / `AWS_REGION` | ⚪ لا | متغير بيئة عادي | ليست أسرارًا. |
| بقية المتغيرات (`PORT`, `LOG_LEVEL`, حدود المعدل…) | ⚪ لا | متغير بيئة عادي | إعدادات لا أسرار. |

**توليد `JWT_SECRET`:**

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

## 3) الإنتاج — متغيرات بيئة المنصّة

تُضبط الأسرار في لوحة المنصّة (ECS task definition / App Service / Container Apps /
Kubernetes Secret… حسب المنصّة) وتصل إلى العملية كمتغيرات بيئة.

قواعد إلزامية:

1. **لا تُخبز الأسرار في الصورة.** الـ`Dockerfile` لا يحوي `ENV` لأي سرّ، ولا يُنسخ `.env`
   (يمنعه `.dockerignore`). الصورة نفسها قابلة للترقية بين البيئات بلا تغيير.
2. **للتخزين على S3 استخدم دور IAM** لا مفاتيح طويلة الأمد. عميل AWS يقرأ الاعتماد
   من سلسلة الافتراضات تلقائيًا (`services/s3Storage.ts`). الصلاحيات المطلوبة على
   الحاوية: `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`.
3. **التدوير:** غيّر القيمة في المنصّة ثم أعد تشغيل النسخ. الإيقاف الرشيق (H0.3)
   يجعل إعادة التشغيل بلا طلبات مقطوعة.

---

## 4) الـCI — GitHub Secrets

`.github/workflows/ci.yml` **لا يحتاج أي سرّ حقيقي**: الاختبارات تعمل على قاعدة
PostgreSQL مؤقتة داخل الـrunner، و`JWT_SECRET` فيه قيمة اختبارية صريحة
(`ci-only-secret-...`) لا تُستخدم في أي بيئة حقيقية — وهذا **أأمن** من حقن السرّ الحقيقي
في وظيفة اختبار.

عند إضافة وظيفة **نشر** لاحقًا، تُقرأ الأسرار من GitHub Secrets:

```yaml
# مثال لوظيفة نشر مستقبلية (غير موجودة بعد)
deploy:
  environment: production # يفعّل مراجعات البيئة وسجلّ النشر
  env:
    JWT_SECRET: ${{ secrets.JWT_SECRET }}
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

قواعد:

- استخدم **GitHub Environments** (`production`) للأسرار الحسّاسة، فتُقيَّد بفرع/مراجعة.
- لا تطبع متغيرات البيئة في خطوات الـworkflow (`env | sort` ممنوع).
- الأسرار محجوبة تلقائيًا في السجلات، لكن **لا تعتمد على ذلك** — لا تمرّرها إلى أوامر تطبعها.

---

## 5) التطوير المحلي

```bash
cp apps/api/.env.example apps/api/.env
# ثم املأ القيم محليًا — الملف مُستثنى من git
```

`.env` المحلي لا يُشارَك ولا يُرفَع. الأسرار الحقيقية تبقى في المنصّة.

---

## 6) ماذا لو تسرّب سرّ؟

1. **دوّره فورًا** في المنصّة (JWT: تدويره يُخرج كل المستخدمين — مقبول عند التسريب).
2. للقاعدة: غيّر كلمة المرور وحدّث `DATABASE_URL`.
3. لمفاتيح AWS: عطّلها في IAM وانتقل إلى دور IAM.
4. إن كان السرّ قد التُزم في git: تدويره **إلزامي** — إزالته من التاريخ وحده لا تكفي
   لأن النسخ المستنسخة تبقى تحمله.
