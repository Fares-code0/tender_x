# دليل النشر

> **الحالة: D0 وD1 مُتحقَّقان · D2 (Render) مكتوب ولم يُنشَر.**
> النسخ الاحتياطي (D3) والـrunbook والمراقبة (D4) لم تبدأ — راجع
> `CLAUDE_CODE_PROMPT_Tender_Deployment.md`.

---

## 1) أين تعيش الصور

| الصورة | المحتوى |
| --- | --- |
| `ghcr.io/fares-code0/tender-api` | حزمة الـAPI المبنيّة على Node 22 |
| `ghcr.io/fares-code0/tender-web` | الواجهة الثابتة + Caddy الذي يخدمها ويبرّكس `/api` |

**الصورتان تُنشران معًا بنفس الوسم** من نفس التشغيل، فلا يقع انزلاق إصدار بينهما.

| الوسم | المعنى | متى يُستعمل |
| --- | --- | --- |
| `v2.2.0` | إصدار موسوم | **الإنتاج** — دائمًا وسم صريح |
| `sha-2be87a7` | نسخة مرتبطة بـcommit بعينه | تشخيص: أي شيفرة بالضبط تعمل الآن |

**لا يوجد وسم `latest` عمدًا.** خادم يسحب `latest` لا يمكن لأحد أن يقول ما الذي يعمل عليه، ولا أن يعيده إلى ما قبله بثقة.

## 2) كيف تُنشر الصور

عند دفع وسم `v*` يعمل [`release.yml`](../../.github/workflows/release.yml) تلقائيًا. وللوسوم القديمة (`v2.0.0`، `v2.1.0`) — لم تكن موجودة يوم أُنشئ الـworkflow فلا تُطلقه بأثر رجعي — يُستعمل التشغيل اليدوي:

```bash
gh workflow run release.yml -f tag=v2.1.0
```

**الترتيب داخل الـworkflow مقصود:** بناء ⇒ اختبار دخان (27 فحصًا) ⇒ دفع. صورة تفشل الدخان **لا تصل السجلّ إطلاقًا**، ثم تُسحب المنشورة على runner نظيف وتُشغَّل للتأكد من أن ما وصل السجلّ يعمل فعلًا.

## 3) سحب صورة وتشغيلها

السجلّ خاص، فيلزم الدخول أولًا برمز وصول شخصي له صلاحية `read:packages`:

```bash
echo "$GITHUB_TOKEN" | docker login ghcr.io -u <username> --password-stdin
```

ثم:

```bash
docker pull ghcr.io/fares-code0/tender-api:v2.1.0
```

التشغيل يحتاج قاعدة بيانات وسرًّا. **السرّ يُمرَّر وقت التشغيل ولا يُخبز في الصورة إطلاقًا** (H7.3)، ويجب أن يكون عشوائيًا ولا يقل عن 16 حرفًا وإلا رفض التطبيق الإقلاع (H0.1):

```bash
docker run -d --name tender_api -p 4000:4000 -e DATABASE_URL='postgresql://user:pass@host:5432/tender' -e JWT_SECRET="$(openssl rand -hex 32)" -e NODE_ENV=production ghcr.io/fares-code0/tender-api:v2.1.0
```

### التحقق من أنها تعمل

```bash
curl -fsS http://localhost:4000/livez
```

| المسار | المتوقع | ماذا يثبت |
| --- | --- | --- |
| `/livez` | `{"status":"live"}` | العملية حيّة (لا يلمس القاعدة) |
| `/readyz` | `{"status":"ready"}` | `SELECT 1` عبر Prisma نجح ⇒ القاعدة موصولة والمحرّك سليم |
| `/v1/tenders` | `401` | التطبيق يخدم مساراته فعلًا لا فحوص الصحة فقط |

`/readyz` يردّ **503** إن تعذّر الوصول للقاعدة — وهذا هو المسار الذي يجب أن يعتمده أي موازن أحمال، لا `/livez`.

## 5) النشر على Render (D2 — **مكتوب ولم يُنشَر بعد**)

> ⚠️ لم يُنفَّذ نشر واحد حتى الآن. ما يلي هو التصميم كما كُتب، ويبقى
> **غير مُتحقَّق** حتى يعمل مرة واحدة على Render فعليًا.

**لماذا Render:** يحفظ الأصل الواحد ويُسقط عبء صيانة الخادم (نظام التشغيل،
الشهادات، النسخ الاحتياطي) — وهو ما يناسب نشرًا للعرض.

### الشكل

```
الإنترنت
   │  HTTPS (شهادة من حافة Render)
   ▼
tender-web   ← الخدمة العامّة الوحيدة (Caddy)
   │  HTTP على الشبكة الداخلية
   ├─ /api/*  ⇒  tender-api   (خدمة خاصّة — بلا عنوان عام)
   │                  │
   └─ غير ذلك ⇒ ملفات الواجهة       ▼
                              tender-db (داخلية)
```

**الأصل الواحد محفوظ:** المتصفح يرى مضيفًا واحدًا، فتُرسَل كوكي
`sameSite=strict` كما ينبغي. الـAPI بلا عنوان عام أصلًا، فلا سبيل للوصول
إليه إلا عبر البروكسي.

### الخطوات

**١ — بيانات اعتماد السجلّ.** الصور خاصّة على GHCR. في Render:
Settings → Registry Credentials → أضف اعتمادًا **باسم `ghcr`** بالضبط
(المستخدم: اسمك على GitHub، وكلمة المرور: رمز بصلاحية `read:packages`).
بدونه يفشل سحب الصور عند أول مزامنة.

**٢ — اربط المستودع.** Render → New → **Blueprint** → اختر `tender_x`.
تقرأ Render ملف `render.yaml` من جذر المستودع وتُنشئ الثلاثة معًا: القاعدة،
والخدمة الخاصّة، والخدمة العامّة.

**٣ — املأ ما لا تستطيع Render استنتاجه.** متغيّر واحد فقط مُعلَّم
`sync: false` فتسألك عنه: `WEB_ORIGIN`. اتركه فارغًا في المزامنة الأولى إن
لم تعرف العنوان بعد، ثم اضبطه على عنوان الخدمة العامّة:
`https://tender-web.onrender.com` (أو نطاقك المخصّص) وأعد النشر.

**٤ — زامِن.** Render تسحب الصورتين بالوسم المكتوب في `render.yaml`،
وتُشغّل الهجرات، ثم تُقلع الخدمات.

### كيف تعمل الهجرات

`preDeployCommand` على `tender-api`:

```
./node_modules/.bin/prisma migrate deploy --schema ./prisma/schema.prisma
```

تعمل **مرة واحدة قبل** أن تستقبل النسخة الجديدة أي طلب، وفشلها **يوقف
النشر** فتبقى النسخة العاملة كما هي. نفس دور خدمة `migrate` في compose.

وأداة `prisma` موجودة في صورة التشغيل (تبعية إنتاج)، فلا حاجة إلى صورة
ثانية للهجرات ولا إلى سياق بناء على المنصّة.

### كيف تتكلّم الخدمات

`API_UPSTREAM` يُحقَن من Render نفسها بمضيف الخدمة الخاصّة ومنفذها
(`fromService … property: hostport`) — لا عنوان مكتوب يدويًا يمكن أن يتقادم.
والمرور كلّه على الشبكة الداخلية.

### أين ترى التطبيق

عنوان الخدمة العامّة: `https://tender-web.onrender.com` — يظهر في لوحة
Render أعلى صفحة الخدمة. TLS من حافة Render، فلا شهادة تُدار ولا تُجدَّد.

### الترقية والتراجع

الوسم مكتوب صراحةً في `render.yaml`:

```yaml
url: ghcr.io/fares-code0/tender-api:v2.2.0
```

**الترقية:** غيّر الوسم في الملف وادفع ⇒ Render تزامن وتنشر.
**التراجع:** أعد الوسم إلى إصدار أقدم وادفع. لا مسار خاص.

> **تنبيه:** التراجع يستبدل الشيفرة لا القاعدة. هجرة حذفت عمودًا لا يعيدها
> وسمٌ أقدم — راجع D3.

### ما لا يُضبط في المستودع

| القيمة | أين |
| --- | --- |
| `JWT_SECRET` | تولّده Render عشوائيًا (`generateValue`) ولا يراه أحد |
| `DATABASE_URL` | تحقنه Render من القاعدة |
| `WEB_ORIGIN` | يدويًا في اللوحة بعد أول نشر |
| اعتماد `ghcr` | يدويًا في إعدادات Render |

**لا سرّ في المستودع ولا في الصورة** — نفس قاعدة H7.3.

## 6) الهجرات

أداة `prisma` **تبعية إنتاج** لا تطوير، فتصل إلى صورة التشغيل ويستطيع خادم لا يملك سياق البناء تطبيق هجرة:

```bash
docker compose run --rm migrate
```

وهي **خطوة نشر منفصلة تعمل مرة واحدة**، لا عند إقلاع كل نسخة: نسخ متوازية تتسابق على الهجرة نفسها.

للتحقق من حالة الهجرات على بيئة تعمل:

```bash
docker compose exec api ./node_modules/.bin/prisma migrate status --schema ./prisma/schema.prisma
```

> **لماذا صورة واحدة لا صورتان:** البديل كان نشر صورة ثانية من مرحلة `build` للهجرات. صورتان منفصلتان تنزلق إحداهما عن الأخرى في الإصدار، والأداة والعميل هنا من قفل واحد فتطابُق إصداريهما مضمون. الثمن زيادة في حجم صورة التشغيل — مقبول مقابل إسقاط صنف كامل من أعطال عدم التطابق.
