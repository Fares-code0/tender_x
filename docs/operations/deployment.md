## 1) أين تعيش الصور

| الصورة | المحتوى |
| --- | --- |
| `ghcr.io/fares-code0/tender-api` | حزمة الـAPI المبنيّة على Node 22 |
| `ghcr.io/fares-code0/tender-web` | الواجهة الثابتة + Caddy الذي يخدمها ويبرّكس `/api` |

**الصورتان تُنشران معًا بنفس الوسم** من نفس التشغيل، فلا يقع انزلاق إصدار بينهما.

| الوسم | المعنى | متى يُستعمل |
| --- | --- | --- |
| `v2.2.0` | إصدار موسوم | **الإنتاج** — دائمًا وسم صريح |
| `sha-2be87a7` | نسخة مرتبطة بـcommit بعينه | تشخيص: أي شيفرة بالضبط تعمل الآن |

**لا يوجد وسم `latest` عمدًا.** خادم يسحب `latest` لا يمكن لأحد أن يقول ما الذي يعمل عليه، ولا أن يعيده إلى ما قبله بثقة.

## 2) كيف تُنشر الصور

عند دفع وسم `v*` يعمل [`release.yml`](../../.github/workflows/release.yml) تلقائيًا. وللوسوم القديمة (`v2.0.0`، `v2.1.0`) — لم تكن موجودة يوم أُنشئ الـworkflow فلا تُطلقه بأثر رجعي — يُستعمل التشغيل اليدوي:

```bash
gh workflow run release.yml -f tag=v2.1.0
```

**الترتيب داخل الـworkflow مقصود:** بناء ⇒ اختبار دخان (27 فحصًا) ⇒ دفع. صورة تفشل الدخان **لا تصل السجلّ إطلاقًا**، ثم تُسحب المنشورة على runner نظيف وتُشغَّل للتأكد من أن ما وصل السجلّ يعمل فعلًا.

## 3) سحب صورة وتشغيلها

السجلّ خاص، فيلزم الدخول أولًا برمز وصول شخصي له صلاحية `read:packages`:

```bash
echo "$GITHUB_TOKEN" | docker login ghcr.io -u <username> --password-stdin
```

ثم:

```bash
docker pull ghcr.io/fares-code0/tender-api:v2.1.0
```

التشغيل يحتاج قاعدة بيانات وسرًّا. **السرّ يُمرَّر وقت التشغيل ولا يُخبز في الصورة إطلاقًا** (H7.3)، ويجب أن يكون عشوائيًا ولا يقل عن 16 حرفًا وإلا رفض التطبيق الإقلاع (H0.1):

```bash
docker run -d --name tender_api -p 4000:4000 -e DATABASE_URL='postgresql://user:pass@host:5432/tender' -e JWT_SECRET="$(openssl rand -hex 32)" -e NODE_ENV=production ghcr.io/fares-code0/tender-api:v2.1.0
```

### التحقق من أنها تعمل

```bash
curl -fsS http://localhost:4000/livez
```

| المسار | المتوقع | ماذا يثبت |
| --- | --- | --- |
| `/livez` | `{"status":"live"}` | العملية حيّة (لا يلمس القاعدة) |
| `/readyz` | `{"status":"ready"}` | `SELECT 1` عبر Prisma نجح ⇒ القاعدة موصولة والمحرّك سليم |
| `/v1/tenders` | `401` | التطبيق يخدم مساراته فعلًا لا فحوص الصحة فقط |

`/readyz` يردّ **503** إن تعذّر الوصول للقاعدة — وهذا هو المسار الذي يجب أن يعتمده أي موازن أحمال، لا `/livez`.

## 5) النشر على خادم (D2 — **مكتوب ولم يُشغَّل بعد**)

> ⚠️ لا خادم حتى الآن، فلم يُنفَّذ أي نشر. ما يلي هو التصميم كما كُتب، ويبقى
> **غير مُتحقَّق** حتى يعمل مرة واحدة على خادم حقيقي.

### تجهيز الخادم لمرة واحدة

```bash
mkdir -p /opt/tender && cd /opt/tender
```

انسخ `.env.production.example` إليه باسم `.env.production`، واملأه، ثم:

```bash
chmod 600 .env.production
```

ولّد الأسرار **على الخادم** لا على جهازك: `openssl rand -hex 32` لـ`JWT_SECRET`، و`openssl rand -base64 32` لكلمة مرور القاعدة.

### النشر

من تبويب Actions، شغّل **Deploy** واختر الوسم والبيئة. لا نشر تلقائي عند الدمج: دمج شيء في `main` لا يعني أن أحدًا مستعد لتحمّل تبعاته على الإنتاج الآن.

ما يفعله الـworkflow بالترتيب: ينسخ `docker-compose.prod.yml` **من الوسم نفسه** إلى الخادم، ثم يسحب الصور، ثم **يطبّق الهجرات في خطوة منفصلة**، ثم يستبدل الحاويات، ثم يتحقق من الخارج عبر العنوان العام بشهادة حقيقية.

ترتيب الهجرات قبل استبدال الحاويات مقصود: فشلها يوقف النشر **قبل** أن تُمسّ النسخة العاملة.

### التراجع

ليس مسارًا خاصًا — شغّل **Deploy** بوسم أقدم:

```bash
gh workflow run deploy.yml -f tag=v2.1.0 -f environment=production
```

لهذا تُنشر الصور بوسوم صريحة ولا يُستعمل `latest` أبدًا: خادم يسحب `latest` لا يمكن إعادته إلى ما قبله بثقة.

> **تنبيه:** التراجع يستبدل الشيفرة لا القاعدة. هجرة حذفت عمودًا لا يعيده وسمٌ أقدم — راجع D3 للنسخ الاحتياطي والاستعادة.

### الأسرار المطلوبة في GitHub

لكل بيئة (`staging` و`production`) على حدة، في إعدادات Environments:

| السرّ | ما هو |
| --- | --- |
| `SSH_HOST` | عنوان الخادم |
| `SSH_USER` | مستخدم النشر (غير جذر) |
| `SSH_KEY` | المفتاح الخاص للنشر |
| `GHCR_PULL_TOKEN` | رمز بصلاحية `read:packages` لسحب الصور |

ومتغيّر (لا سرّ): `SITE_ADDRESS` — النطاق، يُستعمل في التحقق بعد النشر.

**أنشئ المفاتيح والأسرار بنفسك.** لا تُمرَّر عبر محادثة ولا تُودَع في المستودع.

## 6) الهجرات

أداة `prisma` **تبعية إنتاج** لا تطوير، فتصل إلى صورة التشغيل ويستطيع خادم لا يملك سياق البناء تطبيق هجرة:

```bash
docker compose run --rm migrate
```

وهي **خطوة نشر منفصلة تعمل مرة واحدة**، لا عند إقلاع كل نسخة: نسخ متوازية تتسابق على الهجرة نفسها.

للتحقق من حالة الهجرات على بيئة تعمل:

```bash
docker compose exec api ./node_modules/.bin/prisma migrate status --schema ./prisma/schema.prisma
```

> **لماذا صورة واحدة لا صورتان:** البديل كان نشر صورة ثانية من مرحلة `build` للهجرات. صورتان منفصلتان تنزلق إحداهما عن الأخرى في الإصدار، والأداة والعميل هنا من قفل واحد فتطابُق إصداريهما مضمون. الثمن زيادة في حجم صورة التشغيل — مقبول مقابل إسقاط صنف كامل من أعطال عدم التطابق.
